# Migrating to Katenary v4

Katenary v4 introduces breaking changes in the labels used as input and in the
labels added to the generated Kubernetes objects. Katenary refuses to convert a
project that still uses an old label prefix, and lists the labels to update.

## Input labels

### From v3

The prefix changes from `katenary.v3/` to `katenary.v4/`. Label names are
unchanged:

| v3 | v4 |
| --- | --- |
| `katenary.v3/ports` | `katenary.v4/ports` |
| `katenary.v3/ingress` | `katenary.v4/ingress` |
| `katenary.v3/same-pod` | `katenary.v4/same-pod` |
| `katenary.v3/health-check` | `katenary.v4/health-check` |
| ... | ... |

See the [labels reference](labels.md) for the complete list.

### From v1 / v2

v1 and v2 used the `katenary.io/` prefix and some labels were renamed:

| v1 / v2 | v4 |
| --- | --- |
| `katenary.io/ports` | `katenary.v4/ports` |
| `katenary.io/ingress` | `katenary.v4/ingress` |
| `katenary.io/same-pod` | `katenary.v4/same-pod` |
| `katenary.io/ignore` | `katenary.v4/ignore` |
| `katenary.io/mapenv` | `katenary.v4/map-env` |
| `katenary.io/secret-vars` | `katenary.v4/secrets` |
| `katenary.io/healthcheck` | `katenary.v4/health-check` |
| `katenary.io/env-to-service` | `katenary.v4/env-from` |
| `katenary.io/configmap-volumes` | `katenary.v4/configmap-files` |

`katenary.io/secret-envfiles` and `katenary.io/empty-dirs` have no direct
equivalent: use `katenary.v4/configmap-files`, `katenary.v4/exchange-volumes`
or a compose volume depending on what you need.

Labels can also be set from a `katenary.yaml` file, using the unprefixed keys
(`ports`, `ingress`, ...). A prefixed key in that file (for example
`katenary.v3/ports`) is rejected with the same error.

## Generated labels

The labels added to Deployments, Services, Ingresses and other objects now
follow the [Kubernetes recommended labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/):

| Before | Now |
| --- | --- |
| `katenary.v3/name` | `app.kubernetes.io/name` |
| `katenary.v3/instance` | `app.kubernetes.io/instance` |
| `katenary.v3/component` | `app.kubernetes.io/component` |
| `katenary.v3/chart-version` | `helm.sh/chart` |
| `katenary.v3/app-version` | `app.kubernetes.io/version` |
| - | `app.kubernetes.io/managed-by` |

The internal annotations are stable and keep the `katenary.io/` prefix:
`katenary.io/version` and `katenary.io/compose-hash`.

!!! warning "The Deployment selector is immutable"
    `app.kubernetes.io/name`, `app.kubernetes.io/instance` and
    `app.kubernetes.io/component` are part of `spec.selector`. A chart
    generated by v4 cannot be applied with `helm upgrade` over a release
    created by an older chart: delete the existing resources first, or keep
    the previous chart until the release can be recreated.

## Ingress

- The default ingress class remains `-` (the controller default). Set
  `class: traefik` in the `katenary.v4/ingress` label to target Traefik.
- `type: ingressroute` generates a Traefik `IngressRoute`
  (`traefik.io/v1alpha1`) instead of the standard Kubernetes Ingress.
- TLS is enabled by default; the `websecure` entrypoint is only added to the
  IngressRoute when TLS is enabled.

## CronJobs

The `katenary.v4/cronjob` command is now wrapped in `sh -c` (unless it already
starts with a shell), and the Job restarts failed pods with
`restartPolicy: OnFailure`.
